# Voronka — сквозной конвейер заявок: сайт → amoCRM → BotHelp → amoCRM

Заявка с формы попадает в amoCRM сделкой и контактом, Telegram-бот на BotHelp
квалифицирует клиента, итог диалога возвращается в карточку сделки. Между
конструкторами стоит слой надёжности на Python: идемпотентность по натуральному
ключу, append-only журнал событий, ретраи с экспоненциальным backoff и очередь
ошибок с ручным разбором.

**Зачем проект существует.** amoCRM и BotHelp спрашивают в каждой второй
вакансии по автоматизации продаж в СНГ. Опыта с этими конструкторами у меня не
было — это первое погружение в них, и README написан именно с этой позиции.
Сильная сторона, которую проект показывает, другая: что происходит на стыке
конструкторов, когда вебхук приходит дважды, а CRM в этот момент лежит.

## Схема потока

```
  форма на сайте                     Telegram + BotHelp
        │  POST /webhook/form               │  «Внешний запрос»
        │                                   │  POST /webhook/bothelp
        ▼                                   ▼
  ┌──────────────────────────────────────────────────┐
  │  Voronka (FastAPI)                               │
  │                                                  │
  │  1. натуральный ключ  ← нормализация телефона    │
  │  2. INSERT OR IGNORE в реестр ключей (inbox)     │
  │     дубль? → журнал, 200, выход                  │
  │  3. запись в append-only журнал                  │
  │  4. задание в очередь (outbox)  → ответ 202      │
  │  ────────────────────────────────────────────    │
  │  воркер: забрать задание → отправить в amoCRM    │
  │     успех     → done + latency в журнал          │
  │     5xx/429   → backoff + джиттер, вернуть в очередь │
  │     4xx       → сразу в DLQ, попытки не жечь     │
  │     бюджет исчерпан → DLQ + ручной replay        │
  └──────────────────────────────────────────────────┘
                         │
                         ▼
                     amoCRM API v4
        POST /api/v4/leads/complex   (сделка + контакт)
        PATCH /api/v4/leads/{id}     (статус, поля, теги)
        POST  /api/v4/leads/{id}/notes (итог диалога)
```

Ключевое решение: **HTTP-обработчик не ходит в amoCRM.** Он фиксирует событие и
отвечает `202 Accepted`, доставка — задача воркера. Поэтому недоступность CRM не
превращается в потерянную заявку, а посетитель сайта не смотрит на спиннер,
пока чужой сервис приходит в себя.

## Измеренные результаты

Полный отчёт с условиями прогона — [docs/measurements.md](docs/measurements.md),
воспроизводится одной командой `python -m bench.run_all`.

Стенд: Windows, Python 3.12.7, всё на `127.0.0.1`, **мок amoCRM**, контроль
дублей самой CRM **выключен** — иначе «ноль лишних сделок» был бы заслугой CRM,
а не слоя идемпотентности.

### A. Идемпотентность

| | |
| --- | --- |
| отправлено заявок | 200 |
| из них уникальных людей | 140 |
| намеренных дублей | 60 |
| **сделок в CRM** | **140** |
| **лишних сделок** | **0** |

Дубли отправлялись **не** байт-в-байт: телефон в другом формате (`+7…` → `8…`),
email в другом регистре, свой `request_id`. Дедуп работает по нормализованному
натуральному ключу, а не по идентификатору доставки.

### B. Отказ внешнего сервиса

amoCRM отдаёт `503` пятнадцать секунд, пока в неё едут 25 заявок.

| | бюджет 8 попыток | бюджет 14 попыток |
| --- | --- | --- |
| приём заявок во время аварии | все 25 за 0.03 с | все 25 за 0.06 с |
| доехало ретраями | 22 | **25** |
| исчерпало бюджет → DLQ | 3 | 0 |
| довезено ручным replay | 3 | — |
| **потеряно событий** | **0** | **0** |

Отдельная находка, а не подтверждение: бюджета в 8 попыток на аварию в 15 секунд
**не хватило**. Разбор — в [docs/pitfalls.md](docs/pitfalls.md), п. 1.

### C. Время прохождения заявки

| | p50 | p95 | max |
| --- | --- | --- | --- |
| ответ формы (202 Accepted) | 0.7 мс | 1.0 мс | 6.7 мс |
| форма → карточка в CRM, одиночная заявка | **78 мс** | 125 мс | 125 мс |
| форма → карточка в CRM, залп 100 заявок | 389 мс | 594 мс | 625 мс |

Две последние строки означают разное: одиночная заявка — то, что видит живой
клиент; залп — плата за один воркер, разбирающий очередь последовательно.
Против боевого amoCRM латентность **не измерялась**.

### D. Одновременные дубли

20 параллельных одинаковых отправок → принято 1, отсечено 19, **сделок в CRM: 1**.
Дедуп через `INSERT OR IGNORE` по первичному ключу: победитель ровно один, даже
когда все запросы приходят в одну миллисекунду.

## Запуск

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
python serve.py
```

`serve.py` поднимает мок amoCRM на 8081 и конвейер на 8080:

* лендинг с формой — http://127.0.0.1:8080/
* журнал событий — http://127.0.0.1:8080/journal
* состояние мока CRM — http://127.0.0.1:8081/_control/leads

Наполнить стенд осмысленными событиями (заявка, дубль, диалог бота, ошибка 400,
короткая авария):

```bash
python -m bench.seed_demo
```

Тесты и замеры:

```bash
python -m pytest -q          # 54 теста
python -m bench.run_all      # 4 сценария замеров -> docs/measurements.md
```

Подключение живого amoCRM: [docs/amocrm-setup.md](docs/amocrm-setup.md).
Секреты — только в `.env` (в `.gitignore`), шаблон в `.env.example`.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/webhook/form` | заявка с формы → `202 accepted` / `200 duplicate` / `422 rejected` |
| `POST` | `/webhook/bothelp` | итог диалога бота, отвечает плоским JSON под JSON Path |
| `GET` | `/api/journal?kind=&limit=` | лента событий |
| `GET` | `/api/stats` | счётчики по типам событий и состояниям очереди |
| `GET` | `/api/dlq` | очередь ошибок |
| `POST` | `/api/dlq/replay` | вернуть задание (или все) в очередь |
| `GET` | `/health` | состояние сервиса и очереди |

Вебхуки закрываются общим секретом `VORONKA_WEBHOOK_TOKEN` в заголовке
`X-Voronka-Token` (пусто = проверка выключена, только для локальных прогонов).

## Как устроен слой надёжности

**Натуральный ключ.** Приоритет: телефон → email → telegram_id. Телефон
нормализуется до цифр с поправкой на `8` → `7`, email приводится к нижнему
регистру (с учётом того, что точки и `+suffix` в gmail не меняют адресата).
Заявка без единого контакта отклоняется с `422`: её физически не с чем
сопоставить. Код и правила — `voronka/keys.py`.

**Реестр ключей (inbox).** `INSERT OR IGNORE` по первичному ключу в одной
транзакции: первый писатель выигрывает, остальные получают `duplicate` и
увеличивают счётчик `hits`. Это работает и при одновременных запросах —
проверено тестом на 16 потоков и замером D.

**Append-only журнал.** Запрет на `UPDATE`/`DELETE` висит триггерами на самой
таблице, а не на договорённости в коде. В журнал пишутся `received`,
`duplicate`, `delivered`, `retry`, `dlq`, `rejected`, `requeued` — с `trace_id`,
номером попытки и латентностью доставки.

**Transactional outbox.** Приём и доставка разделены: HTTP-обработчик коммитит
задание, воркер доставляет. Задания берутся по возрастанию `id`, поэтому
`create_lead` не обгоняет `update_lead` для одного лида.

**Классификация ошибок.** `408/425/429/5xx` и сетевые таймауты — повторяем;
остальные `4xx` — сразу в DLQ. `PATCH` сделки, которой ещё нет, считается
ретраебельной ситуацией, а не ошибкой: итог диалога бота может прийти раньше,
чем создалась сделка.

**Backoff.** `min(cap, base·2^(n-1))` с полным джиттером. Джиттер обязателен:
без него пачка заданий возвращается синхронно и добивает сервис, который только
начал вставать. Плата за джиттер — недетерминированность бюджета попыток, см.
грабли, п. 1.

## Что осознанно не сделано

* **Один воркер.** Горизонтальное масштабирование потребовало бы шардирования
  очереди по `dedup_key`; для потока заявок с сайта это преждевременно.
* **SQLite, а не Postgres.** Проект должен подниматься одной командой без
  внешних зависимостей. Схема переносится на Postgres без изменений логики:
  `INSERT OR IGNORE` → `ON CONFLICT DO NOTHING`, триггеры — почти дословно.
* **n8n не используется.** Задание допускало n8n или Python. Выбран Python:
  идемпотентность, классификация ошибок и append-only журнал в n8n собираются
  из узлов, которые нечем покрыть тестами и неудобно версионировать. Готовность
  работать в n8n это не отменяет — просто здесь он был бы слабее.
* **Своей UI-имитации карточки amoCRM нет.** Скриншот «карточки сделки» из мока
  выглядел бы как настоящий amoCRM и вводил бы в заблуждение. Состояние сделки
  после диалога показано JSON'ом мока; настоящий скриншот появится, когда
  подключится триал.

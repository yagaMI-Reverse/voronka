# Подключение живого аккаунта amoCRM

Конвейер работает против мока из коробки. Чтобы переключить его на боевой
аккаунт, нужно пройти пять шагов. Ниже — то, что подтверждено документацией
amoCRM; шаги в интерфейсе помечены **[UI]** и на момент написания в живом
аккаунте не проходились.

---

## 1. Триал **[UI]**

Регистрация аккаунта — вручную, на amocrm.ru / amocrm.kz. Бесплатный период —
14 дней, этого достаточно, чтобы снять все скриншоты и прогнать сквозной тест.
Поддомен из адреса аккаунта (`https://<поддомен>.amocrm.ru`) идёт в `AMO_BASE_URL`.

---

## 2. Интеграция и токен **[UI]**

`Настройки → Интеграции → Создать интеграцию` (внешняя или приватная).

Два варианта авторизации, оба поддержаны кодом:

### Долгосрочный токен — проще (`AMO_AUTH_MODE=long_lived`)

Появился в феврале 2024. Срок жизни выбирается при выдаче: от 1 дня до 5 лет,
`refresh_token` не выдаётся, обновлять ничего не нужно. Подходит для приватной
интеграции под один аккаунт — ровно наш случай.

> Токен показывается **один раз** при создании. Не скопировали — выпускайте
> заново. Отозвать можно на вкладке «Выданные доступы».

```env
AMO_AUTH_MODE=long_lived
AMO_LONG_LIVED_TOKEN=<токен>
AMO_BASE_URL=https://<поддомен>.amocrm.ru
```

### OAuth2 — если интеграция публичная (`AMO_AUTH_MODE=oauth`)

Обмен `authorization_code` на пару токенов, дальше — `refresh_token`.

* `access_token` живёт 24 часа (`expires_in: 86400`);
* `refresh_token` живёт 3 месяца и **одноразовый**: после обмена старый
  недействителен. Если не сохранить новую пару — доступ потерян и нужна
  повторная авторизация руками;
* эндпоинт: `POST https://<поддомен>.amocrm.ru/oauth2/access_token`.

```env
AMO_AUTH_MODE=oauth
AMO_CLIENT_ID=...
AMO_CLIENT_SECRET=...
AMO_REDIRECT_URI=https://.../amo/callback
AMO_AUTH_CODE=<одноразовый код, нужен только при первом запуске>
```

Токены складываются в таблицу `oauth_tokens` в БД конвейера и обновляются
автоматически: на `401` клиент делает один refresh и повторяет запрос.

## 3. Воронка, статусы и поля **[UI]**

В интерфейсе создать в воронке нужные этапы и кастомные поля сделки:
источник, бюджет, сроки, Telegram.

Дальше — не выковыривать ID глазами, а забрать их из API:

```bash
python -m tools.discover_amo
```

Скрипт печатает все воронки со статусами, все кастомные поля сделок и
контактов и предлагает готовые строки для `.env`.

```env
AMO_PIPELINE_ID=...
AMO_STATUS_NEW=...
AMO_STATUS_QUALIFIED=...
AMO_STATUS_REJECTED=...
AMO_CF_SOURCE=...
AMO_CF_BUDGET=...
AMO_CF_TIMELINE=...
AMO_CF_TELEGRAM=...
```

Если ID поля не указан — конвейер просто не отправляет это поле, а не падает.

## 4. Что и как создаётся

Сделка и контакт создаются одним запросом:

```
POST /api/v4/leads/complex
```

Тело — массив сделок, у каждой в `_embedded.contacts` вложен контакт с
`custom_fields_values` по кодам `PHONE` / `EMAIL`. Ответ:

```json
[{"id": 15198335, "contact_id": 19663157, "request_id": ["..."], "merged": false}]
```

Ограничения контракта: не более 50 сделок в запросе, не более 40 кастомных
полей на сущность.

### Про `merged` и контроль дублей amoCRM

Если у интеграции включён контроль дублей, amoCRM сама может привязать сделку
к существующему контакту с тем же телефоном или email и вернуть `merged: true`.

Это **не заменяет** идемпотентность конвейера и не пересекается с ней:

| | контроль дублей amoCRM | идемпотентность конвейера |
| --- | --- | --- |
| что склеивает | контакт | заявку целиком |
| вторая **сделка** | всё равно создаётся | не создаётся |
| работает при недоступности CRM | нет | да, ключ проверяется до запроса |
| виден в журнале | нет | да, событие `duplicate` |

Поэтому в замерах (`bench/run_all.py`) контроль дублей мока **выключен**:
иначе «ноль лишних сделок» был бы заслугой CRM, а не нашего слоя.

## 5. Проверка

```bash
python -m voronka --port 8080
curl -X POST http://127.0.0.1:8080/webhook/form ^
  -H "Content-Type: application/json" ^
  -d "{\"name\":\"Тест\",\"phone\":\"+77071234567\"}"
```

Ожидаемо: `202 accepted`, через секунду в журнале `/journal` появляется
`delivered`, в amoCRM — сделка с контактом. Повторный тот же запрос должен
вернуть `duplicate`, и вторая сделка не появиться.

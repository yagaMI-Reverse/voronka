# BotHelp: сценарий автоворонки и выход наружу

Документ описывает (1) что именно собирается в конструкторе, (2) как BotHelp
отдаёт данные во внешний сервис, (3) где конструктор упирается в потолок.

**Статус:** конструктор — первый опыт, аккаунт на момент написания не подключён.
Всё, что помечено **[UI]**, — план сборки, который надо пройти руками и после
этого дописать раздел «грабли». Всё, что помечено **[док]**, взято из
документации BotHelp.

---

## 1. Карта сценария

```
deep-link t.me/<bot>?start=lead_<dedup_key>
        │
        ▼
  [1] Приветствие + запрос согласия продолжить
        │  кнопка «Да, давайте» / «Позже»
        ├──────── «Позже» ──► тег cold ──► напоминание через 1 день
        ▼
  [2] Вопрос: какая задача?
        кнопки: бот в Telegram | интеграция с CRM | и то, и другое
        сохранить в переменную {{task}}
        │
        ▼
  [3] Вопрос: бюджет?
        кнопки: до 150 тыс ₸ | 150–500 тыс ₸ | больше | пока не знаю
        сохранить в {{budget}}
        │
        ├── «до 150 тыс ₸» или «пока не знаю» ──► тег cold ──────┐
        ▼                                                        │
  [4] Вопрос: сроки?                                             │
        кнопки: срочно | этот месяц | планирую                   │
        сохранить в {{timeline}}                                 │
        │                                                        │
        ├── «планирую» ──► тег warm ──────────────────────────┐  │
        ▼                                                     │  │
  [5] Тег hot + «менеджер напишет в течение часа»             │  │
        │                                                     │  │
        ▼                                                     ▼  ▼
  [6] Действие «Внешний запрос» → POST /webhook/bothelp  ◄──────┘
        тело: телефон/telegram_id, qualified, budget, timeline, segment
        ответ: $.lead_id → сохранить в поле подписчика {{amo_lead_id}}
        │
        ▼
  [7] Цепочка напоминаний (только для тех, кто не дошёл до [5]):
        +1 день  → «остались вопросы?»
        +3 дня   → кейс + оффер
        +7 дней  → последнее касание, затем тег lost
```

Ветвление сделано так, чтобы **любой** выход из воронки заканчивался вызовом
`/webhook/bothelp`: и «горячий», и «холодный». Иначе в CRM попадают только те,
кто дошёл до конца, а это ровно та половина данных, которая никому не нужна.

## 2. Переменные подписчика **[UI]**

| Переменная в BotHelp | Куда едет | Тип |
| --- | --- | --- |
| `{{phone}}` | `phone` — участвует в ключе дедупликации | телефон |
| `{{telegram_id}}` | `telegram_id` — запасной ключ, если телефона нет | текст |
| `{{task}}` | попадает в `transcript` | текст |
| `{{budget}}` | `budget` → кастомное поле сделки | текст |
| `{{timeline}}` | `timeline` → кастомное поле сделки | текст |
| `{{segment}}` | `segment` → тег сделки (hot/warm/cold/lost) | текст |
| `{{amo_lead_id}}` | заполняется **ответом** конвейера, `$.lead_id` | число |

Телефон в Telegram-боте не появляется сам: его нужно либо спросить кнопкой
«Отправить номер» (запрос контакта), либо принести из формы через deep-link.
Если телефона нет вообще — ключ считается по `telegram_id`, поэтому его надо
передавать всегда.

## 3. Как BotHelp отдаёт данные наружу **[док]**

Три механизма, разные по цене и гибкости:

### 3.1 Действие «Внешний запрос» — основной путь

* поддерживает `GET`, `POST`, `PUT`, `PATCH`, `DELETE`;
* в URL, заголовках и теле подставляются макросы (значения полей подписчика);
* ответ разбирается через **JSON Path**, значение кладётся в поле подписчика:
  например, `$.name` вернёт поле `name` из тела ответа;
* **обязательное условие:** заголовок `Content-Type` должен быть выставлен
  и в запросе, и в ответе сервиса, допустимы только `application/json` и
  `text/html`. Без этого маппинг ответа не работает — это отдельно оговорено
  в документации;
* есть режим тестовых значений: при тесте вместо макросов подставляются
  заданные тестовые данные.

Настройки для этого проекта:

```
Метод:  POST
URL:    https://<ваш-домен>/webhook/bothelp
Заголовки:
        Content-Type: application/json
        X-Voronka-Token: <значение VORONKA_WEBHOOK_TOKEN>
Тело:
{
  "phone": "{{phone}}",
  "telegram_id": "{{telegram_id}}",
  "qualified": true,
  "budget": "{{budget}}",
  "timeline": "{{timeline}}",
  "segment": "{{segment}}",
  "transcript": "Задача: {{task}}\nБюджет: {{budget}}\nСроки: {{timeline}}",
  "step_id": "qualification"
}
Маппинг ответа:
        $.lead_id  ->  поле подписчика amo_lead_id
        $.status   ->  поле подписчика last_sync_status
```

Ответ конвейера намеренно плоский — `{"status", "trace_id", "lead_id", "detail"}` —
чтобы JSON Path был односложным. Вложенность здесь работает против вас.

**`step_id` — не косметика.** Он входит в ключ идемпотентности шага: если BotHelp
повторит вызов (ретрай на их стороне, повторный проход человека по ветке),
второе примечание в сделке не появится. Разным шагам сценария нужно давать
разные `step_id`, одинаковым повторам — одинаковый.

### 3.2 Интеграция через ApiWay **[док]**

Готовые коннекторы к сторонним сервисам: поля бота перетаскиваются в поля
принимающей системы. Быстро, но данные едут «как есть» — ни дедупликации, ни
ретраев, ни журнала. Годится для «просто положить строку в таблицу».

### 3.3 API BotHelp

Полноценный доступ к данным подписчиков извне. Нужен, когда инициатива на
стороне вашего сервиса, а не бота.

## 4. Где конструктор упирается в потолок

Разграничение, ради которого проект и делался: **что остаётся в конструкторе,
а что уезжает в код.**

| Задача | Конструктор | Почему |
| --- | --- | --- |
| Приветствие, вопросы, кнопки, ветвление | **да** | это его работа, кодом делать дороже |
| Теги, сегменты, напоминания по расписанию | **да** | встроено |
| Отдать данные наружу одним запросом | **да** | «Внешний запрос» |
| Не создать второго лида при повторе | **нет** | нет понятия «натуральный ключ»; повторный проход = повторный вызов |
| Пережить недоступность CRM | **нет** | нет очереди и ретраев с backoff на стороне сценария |
| Разобрать инцидент «где заявка» | **нет** | нет сквозного журнала попыток по trace_id |
| Отличить 400 (чинить руками) от 503 (повторить) | **нет** | ответ не классифицируется |
| Нормализовать телефон `8…` → `+7…` | частично | макросами можно, но это логика в подписи кнопки |
| Сложное условие на пересечении CRM и бота | **нет** | конструктор не видит состояние сделки |

Отсюда и архитектура: BotHelp остаётся тем, в чём он силён — диалог и
расписание. Всё, что требует гарантий доставки и разбора инцидентов, стоит
за одним HTTP-эндпоинтом и живёт в коде.

## 4.5. Как дать BotHelp достучаться до локального конвейера

BotHelp шлёт запрос из интернета, конвейер живёт на `127.0.0.1` — нужен тоннель.

```bash
python -m tools.expose
```

Скрипт поднимает конвейер и ngrok, а потом **проверяет снаружи**, что через
публичный адрес отвечает именно он: запрос с неверным токеном должен получить
`401`, а заявка без контактных данных — `422`. Только после этого печатает
готовый блок настроек для «Внешнего запроса» с подставленным адресом.

Проверено 28.07.2026: `401` и `422` приходят через тоннель как надо.

Два правила, которые нельзя пропускать:

* **`VORONKA_WEBHOOK_TOKEN` обязателен.** Публичный адрес без общего секрета —
  это открытая дверь: писать заявки в вашу CRM сможет любой, кто узнает URL.
  Скрипт откажется стартовать с пустым токеном;
* **адрес ngrok меняется при каждом перезапуске.** Перезапустили — поменяйте URL
  в настройках «Внешнего запроса», иначе бот будет молча стучаться в никуда.
  Для постоянной работы нужен нормальный хостинг, а не тоннель.

Если BotHelp вдруг получает от ngrok HTML-заглушку вместо ответа сервиса,
добавьте в заголовки запроса `ngrok-skip-browser-warning: true`.

## 5. Чеклист сборки **[UI]**

- [ ] Создать бота в @BotFather, подключить канал Telegram в BotHelp
- [ ] Собрать шаги 1–5, проверить каждую ветку тестовым проходом
- [ ] Завести поля подписчика из таблицы п. 2
- [ ] Настроить «Внешний запрос» по п. 3.1, прогнать тест с тестовыми значениями
- [ ] Убедиться, что `Content-Type: application/json` стоит с обеих сторон
- [ ] Проверить, что `$.lead_id` реально попал в поле подписчика
- [ ] Собрать цепочку напоминаний, проверить, что она не шлётся тем, кто дошёл до конца
- [ ] Пройти воронку с чистого аккаунта целиком и сверить с `/journal`
- [ ] Записать в `docs/pitfalls.md` всё, что повело себя не так, как ожидалось
